# Workflow pressure review — Chief 2.0.0

This is a written scenario and mechanism review of the source and documentation, not a claim that future agents were simulated successfully. Automated fixture results belong to the test-run evidence produced separately. No business repository was migrated, built, or tested for this review.

| Pressure scenario | Required behavior and inspected mechanism | Remaining limit |
| --- | --- | --- |
| A tiny settled repair is rushed; creating roles would dominate the work | A Chief executor can own a current work item without a child. Operations/repairs retain established-behavior evidence, input manifests, prechecks, and acceptance. | Classification and the meaning of retained evidence remain coordinator judgments. |
| A new product is called an operation to avoid discovery | New-product records require full discovery and its Product Manager/four-lane gate. Unresolved decisions cannot be erased by a new work label. | A dishonest classification cannot be detected solely from a string or Boolean. The Chief must compare the change with the actual accepted behavior. |
| An established product changes one area | Require affected discovery and preserve relevant unresolved product decisions; reuse valid unaffected evidence. An unrelated operation/repair under a current gate needs an exact gate-hash/acceptance/surface mapping with retained evidence at admission. | Do not mistake the absence of a whole-project gate for permission to skip affected evidence. |
| A writer labels its second pass independent | Sensitive/high-risk work requires independent mode and a distinct registered read-only reviewer; stagnant-round diagnosis additionally excludes every historical writer. | Registry identity is not cryptographic proof of separate reasoning or real-world identity. |
| Repeated failures invite new IDs, candidates, phases, or owners | Attempt history remains cumulative through acceptance overlap, work identity, goal, and lineage; smaller retained limits win. Two stagnant rounds require diagnosis tied to the exact events and a new path. | Coordinator-owned history is not tamperproof. Relabeling or deleting accepted outcomes/history violates the contract even if done outside the helper. |
| A cosmetic log change is presented as progress | Typed progress requires a criterion, changed before/after observation, allowed kind, retained evidence, and a new evidence hash. | Novel bytes alone do not establish meaningful progress; evidence review remains necessary. |
| Two heavy actions start under unknown capacity | Admission defaults to one heavy task; observations must be fresh within 300 seconds and memory estimates must fit. Unrelated light work remains eligible. | This checks recorded reservations, not every operating-system process. Callers must use admission and reconcile interruptions. |
| A source file changes after static validation | The input manifest hash binds checks; admission rereads retained input proofs. | Correctness depends on declaring all relevant inputs. The system does not discover undeclared dependencies. |
| A build fails or signature validation rejects generated output | The generic build helper preserves declared artifacts before postchecks and distinguishes build, validation, and release eligibility. | Platform validators are explicit adapters; fixture bytes do not prove an actual package signature. |
| Updating installed instructions might overwrite project policy | Thin entries load a pinned source. Managed hashes, legacy recognition, and canonical adapter validation reject conflicting instructions; project overrides remain user-owned. | Unknown manual instructions need review. Independently frozen adapters retain their separate revalidation boundary. |
| A batch includes clean, dirty, conflicting, and missing projects | Fixed-tag source sync creates per-project migration branches/commits; unrelated dirty work uses an isolated worktree; result statuses expose each outcome and processing continues. | Success in an isolated worktree does not integrate the original branch. Integration is explicit and no push is implied. |
| A preview succeeds, then state changes | Apply replans and validates current state; preview is read-only except an explicitly requested report file. | Preview is not a durable authorization receipt. Report parents must exist. |
| A user asks to undo an already integrated migration | Rollback requires an exact local migration SHA and a clean checkout, creates a revert commit, and refuses later managed-file drift. | Conflicts need manual reconciliation; rollback does not remove worktrees or erase history. |
| The installed source is modified locally after pinning | Work admission compares source HEAD/version and managed-project hashes; fleet sync additionally rejects a dirty fixed-tag source. | Work admission does not itself attest every source file is clean. Operators must retain a clean fixed source; neither path guarantees future-agent obedience. |

The earlier documentation contained unconditional project-wide discovery, active-child requirements, and floating-copy installation instructions. Those clauses were scoped or replaced: V1 works per current work, full new-product discovery remains intact, and installation has one fixed source. The full historical project template remains a compatibility fixture, not another V1 implementation.

Review outcome: the documented coordination policy and the implemented admission interfaces are distinguishable, with evidence limits stated. This is not a release authorization, universal compliance guarantee, or a substitute for the root's final regression results and independent policy findings.

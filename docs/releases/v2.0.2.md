# Chief v2.0.2 migration notes

## What changes

Chief now separates evidence calculation from Testing control. The existing
`testing_evidence.py` still authenticates original PASS, Git snapshots and delta
coverage. The new `testing_control.py` cheaply classifies risk, justification,
events, delivery retries, pending modules and creative batches before any
Testing round trip or high-cost reasoning.

The project contract schema remains **2** and `WORK_EXECUTION_V1` remains current.
New freezes use `CHIEF_FROZEN_TESTING_EVIDENCE_V2`, adding evidence ID, timestamp,
result, risk scope and tested path/asset metadata. V1 frozen bundles are accepted
in place; no rewrite or destructive state migration is required.

## Incident replay

| Scenario | v2.0.x behavior | v2.0.2 behavior |
| --- | --- | --- |
| Skill install + empty Testing | Installation waited after `items=[]` | L0 completes from deterministic local checks; zero Testing round trips |
| Ali candidate pending | Finished static work entered wait | Candidate stays ready/pending and another runnable module continues |
| Creative visual loop | Every revision opened Testing/wait | Five unchanged-risk revisions produce zero Testing round trips; risk is batched once |
| APK fast path + dependency ready | READY telemetry preempted build work | READY is record-only; `BUILD_SUCCEEDED` is consumed first |
| Integration of tested parts | Passed modules were resubmitted | Module PASS is inherited and only `integration-smoke` is requested |

The executable fixture is `tests/fixtures/testing-control-v2.0.2.json`; the
`dogfood` command returns the before/after decision records from production
policy functions.

## Validation record

- Baseline `v2.0.1`: 362 tests; 361 passed, one optional skip, zero failures.
- v2.0.2 targeted control/evidence/sync/build run after repair cycle 2: 79 passed, zero failures.
- v2.0.2 full regression after repair cycle 2: 386 tests; 385 passed, one optional skip, zero failures.
- New automated regressions: 24, including repair-cycle cases that reject a
  PASS/FAIL status when delivery items are missing, null, empty, telemetry-only,
  unbound to the candidate, or otherwise not a valid gate receipt.
- Dogfood: five incident workflows replayed with the expected non-wait/non-repeat behavior.
- Python compile and `git diff --check`: passed.

The bundled Skill quick-validator could not start because its own runtime lacked
PyYAML; no dependency was installed. Frontmatter/placeholder checks, Python
compilation and repository regression passed independently.

Known architecture boundary: the repository can classify telemetry before Chief
reasoning only when the host routes native event envelopes through the classifier.
It cannot patch the host's pre-wake delivery layer. If the host has already woken
the model, policy requires one minimal classifier call and no subsequent
reasoning/scheduling turn. No other unresolved Testing-control behavior is known
in the covered repository and simulated workflows.

Repair provenance: independent review and the Testing Chief both rejected R1
commit `75ba4b8fd75196b8acb879963f4e83431495e104` because a PASS/FAIL status with
missing/null delivery items could be accepted as a verdict. The retained R1
remains failed. Repair cycle 1 requires a nonempty list of delivery items and
adds the falsification regression before freezing R2.

Testing Chief rejected R2 `95532a3946a94d358bcead2e6ae199a9b8439935`
because nonempty but invalid items such as `[{}]`, `[null]`, or an ACK could still
be accepted. Repair cycle 2 requires a structured candidate-bound gate receipt,
matching verdict/issuer, and no unresolved findings for PASS before freezing R3.

## Adopt

Use one clean source checkout fixed at `v2.0.2`:

```bash
git -C /path/to/chief-source fetch origin tag v2.0.2
git -C /path/to/chief-source switch --detach v2.0.2
```

Preview, then sync the selected existing projects sequentially:

```bash
python3 /path/to/chief-source/scripts/chief_sync.py fleet-sync --source /path/to/chief-source --projects /path/to/projects.json --pinned --dry-run --report /path/to/reports/chief-sync-preview.json
python3 /path/to/chief-source/scripts/chief_sync.py fleet-sync --source /path/to/chief-source --projects /path/to/projects.json --pinned --report /path/to/reports/chief-sync.json
```

Sync updates only Chief-managed files and creates reviewed local migration
commits/worktrees. It does not push, merge, run business tests, build APK/AAB,
or adopt the policy for an active old Chief without its explicit reread/adoption.

## Roll back

For a project migration, use the exact full migration commit SHA from its report:

```bash
python3 /path/to/chief-source/scripts/chief_sync.py rollback --target /path/to/project --commit FULL_MIGRATION_COMMIT_SHA --report /path/to/reports/chief-rollback.json
```

For the Chief source, use a separate clean checkout at the previous stable
`v2.0.1`, or `v2.0.0` when that older contract is explicitly intended. Do not
move tags, force push, reset a dirty checkout, or erase migration history.
